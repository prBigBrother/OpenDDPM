# UI review — 20 October 2026

This records the initial UI review. The subsequent native SwiftUI refactor
supersedes the custom sidebar/card styling described here; see
[Native SwiftUI UI](NATIVE-SWIFTUI-2026-10-20.md) for the current implementation.

Reviewed the current working tree, including pre-existing uncommitted HomeKit,
hotkey and UI changes. Implementation in this pass is limited to `Views.swift`
and `RemoteView.swift`. The monitor planner, saved presets and Home pairing were
preserved. This is a source review of all UI surfaces plus a live inspection of
the main settings pages, preset editor and remote; it is not a claim that every
hardware or first-run state was exercised.

## Findings and changes

| Surface | Finding | Result |
| --- | --- | --- |
| Navigation | Appearance and login settings were hidden under “About OpenDDPM”. The setup heading did not match its navigation label. | Renamed the destination to “General & about” and setup heading to “Monitor & inputs”. Added a direct remote button. |
| Page navigation | The same scroll container was reused across destinations. | Reset its identity per destination so a newly selected page starts at the top. |
| Monitor & inputs | Monitor selection appeared enabled during operations although the model rejected selection. | Disable that picker while busy, matching the underlying behavior. |
| Preset cards | The confirmed layout was indicated only by a small label/button. | Added accent fill and outline for verified and selected cards. Suppress stale verified styling while a transition is busy. |
| Preset switching | The settings grid blocked every Apply button while busy, while the remote and coordinator supported replacing the target. | Apply remains available for eligible presets during a transition. Added a short explanation. Editing/reordering remain gated during hardware work. |
| Preset visibility | Cards only disclosed hidden-Mac behavior when protection blocked them. With protection off, those cards looked ordinary. | Display “Hides this Mac” in both surfaces even when application is allowed; settings distinguish blocked presets and explain the cause in help text. |
| Incomplete setup | Existing presets could appear as disabled controls without a direct route forward. | Added a setup action in both the grid and remote. |
| Preset editor | A filled name field lost its visible field label. Full-screen input used a split-layout label. Swapping sources required two picker changes. | Persistent name label; Main/Left/Right/Inset input labels appropriate to layout; Swap inputs updates the draft and preview together. |
| Remote footer | Previous preset names could make the footer arbitrarily wide. | Stable “Previous preset” label; destination retained in help. Shortened verification action to “Verify” with explanatory help. |
| Accessibility | Explicit focus exclusions prevented keyboard access to navigation and remote controls. Icon buttons used symbol-derived names. Preview content was announced repeatedly. | Removed those focus exclusions, exposed selected navigation state, named icon actions, grouped preview accessibility, and gave remote cards concise names and explicit status values. |
| Hotkeys | Existing recorder, clear actions and conflict/blocked messages cover the main workflow. | Kept behavior; shared clear-button accessibility improvements apply here. |
| Apple Home | Current UI already separates connection, pairing and advanced service details, and preserves pairing on stop. | Kept current implementation after source review and live inspection of the connected page. No service toggle, reinstall or pairing action performed. |
| Apple Shortcuts sheet | Instructions, stable preset link, copy feedback and Done action are present. | Reviewed in source; kept existing behavior. |
| Menu bar menu | Applies via the shared coordinator; blocked entries and status already exposed. | Reviewed in source; kept existing behavior. |

## Verification

- `scripts/test.sh`: 10 HomeKit-health assertions, 4,204 core assertions,
  32 coordinator/readiness/recovery/deadline assertions and native DDC packet
  validation passed.
- Swift compiled for arm64 and x86_64; `lipo -archs` confirmed both slices.
- The build script stopped at `iconutil: Invalid Iconset`. The local review app
  uses the existing built app's `AppIcon.icns`; no source asset was changed.
  Ad-hoc signing and `codesign --verify --deep --strict` then succeeded.
- Ran `build/ui-review/OpenDDPM.app` and inspected the updated preset grid,
  editor, remote and general settings with native screenshots and accessibility
  state. Confirmed hidden-Mac labels, selected-card styling and concise remote
  accessibility values.
- Exercised Swap inputs in an unsaved draft: Thunderbolt and DisplayPort changed
  sides in both pickers and preview. Cleared its name and confirmed Save became
  disabled. Cancelled the draft without modifying saved presets.
- Inspected light appearance and the system's dark appearance. Restored the
  original System preference after checking light cards and general settings.
- Native focus indicators are visible on newly keyboard-accessible controls.
  A complete VoiceOver or keyboard-only traversal was not performed.
- No Apply, Previous, physical-input, Home enable/disable or pairing action was
  invoked. Busy/blocked/first-run branches were reviewed in source; changing
  targets during a real monitor transition was not exercised in this UI pass.
- `git diff --check` passed.

The review app is separate from `/Applications/OpenDDPM.app` and was left running
on Presets. A screenshot is saved at
`build/ui-review/screenshots/presets-dark.png`.

## Further opportunities

These are additional product changes, not unresolved requirements of this pass:

1. Offer Undo for preset deletion and preview the replacement before importing
   a collection. Both actions currently modify the saved collection immediately.
2. Add name/input filtering if collections grow substantially. Reordering while
   filtered needs an explicit, understandable rule.
3. Consider a common compact status component for settings and remote, including
   an expandable error explanation. Keep selected, applying, verified and
   unavailable states distinct.

Do not add optimistic hardware-success indicators. The current verified state
must continue to come from monitor readback.
